# **1\. Общая информация**

## **1.1. Цель**

Разработать прототипы инструментов, которые автоматически выявляют потенциальные риски корпоративной IT-инфраструктуры, сокращают объём ручных проверок и позволяют обнаруживать проблемы до возникновения инцидента или недоступности сервисов.

## **1.2. Состав направления**

1\. Identity Risk Analyzer \- автоматизированный анализ рисков Microsoft Active Directory.

2\. Certificate Radar \- централизованное обнаружение, инвентаризация и контроль цифровых сертификатов.

## **1.3. Ключевой принцип**

***«Обнаружить проблему до того, как она станет инцидентом»***

# **2\. Проект 1\. Identity Risk Analyzer**

## **2.1. Описание задачи**

Разработать систему автоматического анализа объектов Microsoft Active Directory для выявления потенциально опасных конфигураций, неиспользуемых учётных записей, избыточных привилегий и других факторов риска. Система должна формировать единую оценку риска и предоставлять администратору объяснение причин и рекомендации по устранению.

## **2.2. Цели**

* выявление устаревших и неиспользуемых учётных записей  
* обнаружение избыточных административных прав  
* контроль сервисных и привилегированных учётных записей  
* выявление рисков парольной политики  
* контроль потенциально опасных настроек Active Directory  
* сокращение ручной работы при регулярном аудите AD

## **2.3. Функциональные требования**

### **2.3.1. Анализ пользовательских учётных записей**

* учётные записи, которые длительное время не использовались  
* включённые учётные записи без активности за заданный период  
* учётные записи с параметром Password Never Expires  
* учётные записи с давно не изменявшимся паролем  
* заблокированные и истёкшие учётные записи

### **2.3.2. Анализ сервисных учётных записей**

* неиспользуемые сервисные аккаунты  
* сервисные аккаунты с разрешённым интерактивным входом  
* сервисные аккаунты с избыточными правами  
* сервисные аккаунты с Password Never Expires

### **2.3.3. Анализ привилегий**

Необходимо проверять прямое и вложенное членство в критических административных группах, включая Domain Admins, Enterprise Admins, Schema Admins, Administrators, Account Operators, Server Operators, Backup Operators, DNSAdmins и другие группы, определённые организаторами.

* пользователи с несколькими уровнями административных прав  
* вложенные группы, приводящие к неочевидному повышению привилегий  
* привилегированные учётные записи без активности  
* избыточные административные назначения

### **2.3.4. Анализ парольных и аутентификационных рисков**

* возраст пароля  
* доменная парольная политика  
* пользователи с ослабленными парольными требованиями  
* признаки Password Spray *(это атака на учётные записи, когда злоумышленник берёт один или несколько популярных паролей и пробует их сразу на большом количестве пользователей.)* Brute Force *(перебор паролей для одной учётной записи)* по журналам аутентификации при наличии данных.

**Ограничение безопасности:** решение не должно получать, отображать или хранить пароли пользователей в открытом виде. Проверка слабых/скомпрометированных паролей допускается только безопасным способом.

### **2.3.5. Дополнительные проверки Active Directory**

В рамках дополнительного анализа решение может выполнять следующие проверки:

* выявление неиспользуемых или длительное время неактивных компьютерных учётных записей;  
* выявление учётных записей с SIDHistory, требующих дополнительной проверки;  
* выявление дублирующихся или некорректно настроенных SPN;  
* выявление потенциально опасных настроек Kerberos Delegation;  
* выявление других потенциально рискованных конфигураций Active Directory по выбору команды.

Данные проверки могут рассматриваться как дополнительные и не являются обязательными для минимальной реализации MVP.

## **2.4. Единая оценка риска**

Для каждого найденного события и объекта должен рассчитываться уровень риска. Алгоритм может учитывать критичность правила, тип объекта, наличие административных прав, давность активности и количество одновременно сработавших признаков.

| Уровень | Описание |
| :---- | :---- |
| Critical | Требует немедленной проверки |
| High | Высокий потенциальный риск |
| Medium | Требует планового устранения |
| Low | Информационное замечание |

**Пример: ServiceAccount01 \- Risk Score 85/100 (Critical).** Причины: Password Never Expires; пароль не менялся 730 дней; имеются повышенные права; отсутствует владелец; разрешён интерактивный вход.

## **2.5. Dashboard**

В Web-интерфейсе необходимо отображать общее состояние Active Directory и возможность перейти к деталям по каждому риску.

* AD Security Score (0-100)  
* количество Critical / High / Medium / Low рисков  
* наиболее рискованные учётные записи  
* количество устаревших, сервисных и привилегированных аккаунтов  
* основные категории рисков  
* динамика Risk Score при наличии истории

## **2.6. Рекомендации**

Для каждого найденного риска система должна выводить понятное описание и рекомендуемое действие. Рекомендация не должна автоматически изменять Active Directory в рамках MVP.

## **2.7. Источники данных**

* Active Directory через LDAP / PowerShell  
* Security Event Log на контроллерах домена

## **2.8. MVP для Hackathon**

1\. подключение к тестовому Active Directory

2\. сбор информации об учётных записях

3\. реализация нескольких проверок риска

4\. расчёт оценки риска

5\. Web Dashboard

6\. список найденных проблем с причинами

7\. рекомендации по устранению

8\. экспорт результата в CSV, Excel или HTML

## **2.9. Дополнительные возможности**

* уведомления администраторам  
* история изменения оценки рисков  
* пояснение найденного риска

# **3\. Проект 2\. Certificate Radar**

## **3.1. Описание задачи**

Разработать централизованную систему автоматического обнаружения, инвентаризации и контроля цифровых сертификатов корпоративной инфраструктуры. Система должна заранее предупреждать об истечении срока действия сертификатов, ошибках цепочки доверия и других потенциальных проблемах.

## **3.2. Цели**

* предотвращение простоев из\-за истёкших сертификатов  
* централизованная инвентаризация сертификатов  
* обнаружение ошибок цепочки доверия и несоответствия DNS-имени  
* контроль слабых криптографических параметров  
* назначение владельца/ответственного за сертификат или сервис

## **3.3. Обнаружение сертификатов**

Система должна принимать список серверов, IP-адресов, DNS-имён, URL или сетевых диапазонов и выполнять сканирование TLS-сервисов. Для MVP обязательна проверка HTTPS/TLS на порту 443\.

## **3.4. Получаемая информация**

В результате сканирования система должна получать и отображать основные сведения о TLS-сертификате:

* DNS-имя или IP-адрес сервиса и порт;  
* CN и SAN сертификата;  
* Issuer;  
* Thumbprint;  
* дата окончания действия сертификата;  
* количество дней до окончания срока действия;  
* состояние цепочки доверия;  
* результат проверки соответствия DNS-имени сертификату.

## **3.5. Контроль срока действия**

| Осталось | Статус |
| :---- | :---- |
| более 60 дней | OK |
| 31-60 дней | Information |
| 15-30 дней | Warning |
| 0-14 дней | Critical |
| менее 0 дней | Expired |

*Пороговые значения должны быть настраиваемыми.*

## **3.6. Выявляемые проблемы**

* истёкший сертификат;  
* сертификат, срок действия которого скоро истекает;  
* self-signed сертификат;  
* ошибка цепочки доверия сертификата;  
* несоответствие DNS-имени сервиса значениям CN/SAN сертификата.

## **3.7. Dashboard**

Dashboard должен показывать общее количество сертификатов, их состояние и ближайшие сроки окончания. Необходимо предусмотреть фильтрацию и сортировку по сервису, владельцу, Issuer, сроку действия и статусу.

| Service | Certificate | Expiration | Days Left |
| :---- | :---- | :---- | :---- |
| outlook.company.kz | Sectigo | 10.09.2026 | 21 |
| vpn.company.kz | DigiCert | 15.09.2026 | 26 |
| portal.company.kz | Internal CA | 21.09.2026 | 32 |

## **3.8. Уведомления**

Система должна поддерживать уведомления при достижении заданных порогов. Рекомендуемые пороги: 60, 30, 14, 7 и 1 день до окончания действия. Каналы уведомлений могут включать Email, Microsoft Teams, Telegram или корпоративную систему мониторинга.

## **3.9. Оценка риска**

Каждому сертификату может присваиваться риск с учётом количества дней до окончания, критичности сервиса, ошибок цепочки доверия, криптографических параметров и наличия владельца.

**Пример: web.contoso.com \- Risk Score 90/100 (Critical).** Причины: сертификат истекает через 5 дней; сервис критичный.

## **3.10. Источники данных**

Для работы Certificate Radar используются следующие исходные данные:

* **TLS-сервисы** \- HTTPS и другие сервисы, использующие TLS. Система подключается к указанному сервису и получает предъявляемый им цифровой сертификат для последующего анализа.  
* **DNS** \- используется для разрешения DNS-имён в IP-адреса и проверки соответствия имени сервиса значениям CN/SAN сертификата.  
* **Входной список объектов для сканирования** \- DNS-имена, IP-адреса, URL или сетевые диапазоны, задаваемые пользователем.

## **3.11. MVP для Hackathon**

1. загрузка списка DNS/IP

2\. автоматическое подключение к TLS-сервисам

3\. получение сертификата и его основных атрибутов

4\. определение даты окончания и Days Left

5\. проверка соответствия DNS-имени

6\. базовая проверка цепочки доверия

7\. присвоение статуса OK / Warning / Critical / Expired

8\. Dashboard

9\. экспорт отчёта

10\. уведомление о сертификатах с малым остаточным сроком действия

# **4\. Общие требования к решениям**

## **4.1. Рекомендуемая архитектура**

Архитектура должна быть модульной, чтобы в дальнейшем можно было подключать дополнительные источники данных и новые виды проверок без полной переработки решения.

## **4.2. Требования безопасности**

* работа преимущественно в режиме Read Only  
* минимально необходимые права доступа; Domain Admin не должен быть обязательным для стандартного анализа  
* запрет на хранение и отображение пользовательских паролей  
* журналирование действий системы

## **4.3. Нефункциональные требования**

* понятный интерфейс для системного администратора и специалиста ИБ  
* настраиваемые пороговые значения  
* экспорт результатов

# **5\. Демонстрационный сценарий**

## **5.1. Identity Risk Analyzer**

Команда подключает решение к тестовому стенду домен контроллера и запускает анализ. 

Для выполнения работ необходимо подготовить тестовую среду с контроллером домена Active Directory. Тестовую среду допускается развернуть на рабочем компьютере участника в виде виртуальной машины с операционной системой Windows Server 2019 или выше.

Для создания виртуальной машины может использоваться Microsoft Hyper-V, Oracle VirtualBox, VMware Workstation или другая платформа виртуализации по выбору команды.

На виртуальной машине необходимо установить роль Active Directory Domain Services (AD DS), создать тестовый домен и наполнить его тестовыми объектами, необходимыми для демонстрации работы решения.

Входе демонстрации, система например обнаруживает:

* 10 неактивных пользователей  
* 7 сервисных аккаунтов с Password Never Expires  
* 3 отключенные привилегированные учётные записи  
* 2 пользователя с избыточными правами

**Результат демонстрации:** Dashboard показывает список рисков, причины их возникновения и рекомендации по устранению.

## **5.2. Certificate Radar**

Для выполнения работ необходимо подготовить тестовую среду с несколькими сетевыми сервисами, использующими цифровые сертификаты.

Тестовую среду допускается развернуть на рабочем компьютере участника с использованием одной или нескольких виртуальных машин. В качестве операционной системы может использоваться Windows Server 2019 или выше. Для виртуализации допускается использование Microsoft Hyper-V, Oracle VirtualBox, VMware Workstation или другой платформы по выбору команды.

На виртуальных машинах рекомендуется развернуть несколько тестовых HTTPS-сервисов, например на базе IIS, и назначить им различные сертификаты, позволяющие продемонстрировать работу решения.

В тестовой среде рекомендуется предусмотреть сертификаты с различными состояниями, например:

* корректный действующий сертификат;  
* сертификат с небольшим остаточным сроком действия;  
* истёкший сертификат;  
* self-signed сертификат;  
* сертификат с ошибкой цепочки доверия;  
* сертификат, DNS-имя которого не соответствует CN/SAN сертификата.

Команда загружает в разработанное решение список DNS-имён или IP-адресов тестовых сервисов, запускает сканирование и демонстрирует обнаружение сертификатов, определение их состояния и выявление потенциальных проблем.

**Результат демонстрации:** Dashboard показывает состояние сертификатной инфраструктуры и список сервисов, требующих внимания.

# **6\. Ожидаемый результат и развитие решения**

По итогам Hackathon должны быть представлены работающие прототипы, подтверждающие возможность перехода от ручных проверок инфраструктуры к централизованному риск-ориентированному мониторингу.

В дальнейшем оба решения могут быть объединены в единую платформу Infrastructure Risk Radar с дополнительными модулями:

* Identity Radar \- Active Directory  
* Certificate Radar \- сертификаты  
* DNS Radar \- DNS  
* Service Radar \- доступность сервисов  
* Patch Radar \- обновления серверов  
* Backup Radar \- состояние резервного копирования  
* Infrastructure Risk Score \- единая оценка состояния корпоративной инфраструктуры

      **Итоговая идея**: создать расширяемую платформу, которая автоматически находит технические риски, приоритизирует их и помогает ответственным специалистам устранять проблемы до возникновения инцидента.
